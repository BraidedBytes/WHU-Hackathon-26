# Spoilsport AI cost and call-path research

Checked 2026-09-29. This is evidence for a product decision, not the decision itself. Prices and API behavior should be rechecked before implementation. Repository references describe commit `ecb1f0e`.

## What actually calls a model

| Path | Trigger and payload | Current cost controls and limits | Behavior on failure |
| --- | --- | --- | --- |
| Page classification | In AI mode, the content script scans text blocks. Blocks shorter than 15 characters or without a watchlist title, cast, character, or expanded term are released locally. Other blocks are obscured immediately, queued after 150 ms, and sent in groups of at most 20; up to three groups run concurrently. Each snippet is truncated to 600 characters. The request repeats the relevant film IDs, titles, years, overviews, and character names, plus a JSON schema. | The extension background has an exact `(truncated text, sorted film IDs)` verdict cache in a JavaScript `Map`; it has no size/TTL/persistence policy or in-flight deduplication. It clears on watchlist change, but not on expanded-term or extra-film change. The local proxy caps the upstream completion at 1,600 generated tokens and sets `reasoning_effort: "none"`. | Missing, malformed, low-confidence positive, timeout, or API error leaves the suspect block obscured with a reveal control. A negative verdict releases it regardless of the reported confidence. | 
| Term expansion | The background calls the model once for each wanted film lacking a `spoilsport:terms:<id>` array. This runs at extension startup, on watchlist changes, and when adding a selected title by context menu. It asks for up to 20 extra plot-discussion terms using the film title and year, then saves the result in `chrome.storage.local`. | A saved array, even empty, suppresses later calls. A failure is swallowed, so the next startup/watchlist change can retry. Switching to keyword mode or pausing the shield does **not** disable these calls. The same local proxy applies the 1,600-token cap and no-reasoning setting. | Matching falls back to existing title/cast/character terms; expansion can retry later. Generated terms can increase subsequent match volume and false positives. |
| Recommendation chat | Every send posts the entire in-memory conversation so far, selected film, taste profile, and watchlist titles to `/api/chat`. The server sends a spoiler-safe system prompt and this context through Chat Completions with `reasoning_effort: "low"`; it may then search TMDB once per model-recommended title, up to five. | The route limits request text to 20,000 characters, messages to 20, and each message to 2,000 characters. The prompt asks for a reply under 120 words, but there is **no** `max_completion_tokens` in this route. There is no server-side response cache or token/cost instrumentation. | An OpenAI error returns HTTP 500 to the chat; an unverified TMDB recommendation becomes plain text. |

These details come from the [content script](../../extension/content.js), [matchers and classifier request](../../extension/lib/detect.js), [background worker](../../extension/background.js), [extension proxy](../../app/api/extension/openai/route.ts), [chat route](../../app/api/chat/route.ts), and [chat UI](../../components/ChatModal.tsx). The popup defaults to AI mode ([popup](../../extension/popup.js)). The extension passes a hardcoded `gpt-6-luna` model, but the proxy **discards that value** and uses server-side `OPENAI_MODEL` for both classifier and term expansion. Chat uses that same environment variable ([proxy](../../app/api/extension/openai/route.ts), [chat route](../../app/api/chat/route.ts)). Thus the actual bill cannot be inferred from the extension code or from this note without knowing the user's configured model. No local key was inspected.

The web watchlist and taste profile live in browser `localStorage`; the watchlist is synced to extension `chrome.storage.local`. Film search, adding a film, and recommendation verification call TMDB, not OpenAI. Search is debounced 300 ms; the TMDB helper uses `cache: "no-store"`. These calls are a separate external-service load, and repeated search or verification is not currently cached by the app ([web app](../../app/page.tsx), [TMDB helper](../../lib/tmdb.ts), [movie route](../../app/api/tmdb/movie/%5Bid%5D/route.ts), [chat route](../../app/api/chat/route.ts)).

## Price and token mechanics

For `gpt-6-luna` at OpenAI's **Standard, short-context** rate on 2026-09-29, the published price is **$0.10 per million uncached input tokens, $0.01 per million cached input tokens, $0.125 per million cache-write tokens, and $0.50 per million output tokens**. Batch and Flex are half the Standard rate; Fast mode is double. A different `OPENAI_MODEL`, processing tier, or future price changes the arithmetic. [OpenAI GPT-6 Luna model page](https://developers.openai.com/api/docs/models/gpt-6-luna), [pricing table](https://developers.openai.com/api/docs/pricing).

Use `cost = (uncached input tokens × input rate + cache-write tokens × write rate + cached-read tokens × cached rate + output tokens × output rate) / 1,000,000` for the applicable tier. As an **illustration, not a measured workload**, 100 Standard Luna requests averaging 3,000 uncached input and 400 output tokens would cost about **$0.05**. Request count alone is insufficient: the repeated film context, number and length of candidate blocks, generated JSON, chat history, and model reasoning all change token usage. OpenAI advises reducing requests and tokens, and selecting a smaller model only after checking accuracy ([cost optimization](https://developers.openai.com/api/docs/guides/cost-optimization)). Reasoning and other non-visible generated tokens are billable output, and `max_completion_tokens` includes them ([reasoning guide](https://developers.openai.com/api/docs/guides/reasoning), [token counting](https://developers.openai.com/api/docs/guides/token-counting)).

The 1,600-token classifier/expansion cap limits output exposure per request, but large batches can hit it and produce incomplete JSON. OpenAI notes that structured output can also be refused and that length-limited results must be handled ([structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs)). The chat's 120-word instruction is a style request, not a hard API cap; all prior turns and profile context are resent on each message ([chat route](../../app/api/chat/route.ts)).

OpenAI prompt caching reuses only an identical **prefix**. For GPT-5.6 and later it requires an eligible prefix of at least 1,024 tokens; writing that prefix costs 1.25× ordinary input, with later reads at 0.1×. The classifier's film context sits inside its system message and changes with the relevant film set; the batch of snippets changes on each request. Chat's static instruction precedes the variable profile and watchlist. Cache hits are therefore possible, but should be measured rather than assumed, especially for short prompts or changing watchlists ([prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)). This OpenAI prompt cache is distinct from the extension's verdict `Map`.

## Options for the release decision

| Option | Potential saving | Protection, privacy, and complexity tradeoff |
| --- | --- | --- |
| Reduce AI candidates locally | Fewer model requests and fewer page-text snippets sent out. Tighten names/terms, limit eligible blocks, or use a local suspicion score before classification. | More aggressive filtering can miss implicit spoilers; broad names/AI-expanded terms can blur benign text. Evaluate false negatives and false positives on the existing demo corpus and real pages. |
| Let suspicious text stay obscured without immediate AI classification, with an explicit user-triggered check or reveal | Potentially large reduction when people do not inspect every suspect block. Keyword mode already makes no per-block model calls. | More benign text stays hidden; an extra action may harm browsing flow. This does not itself stop automatic term expansion. |
| Keep live classification but change batching/cache policy | Existing 20-snippet batches amortize repeated context. Deduplicating concurrent identical snippets and bounded caching can save repeat work. | Larger batches wait longer and need more output tokens; stale verdicts are possible when film context or model/prompt changes. Cache keys should reflect all material context. Persisting web text locally increases privacy footprint. |
| Make term expansion selective, metadata-driven, or manual | Removes or limits one model call per protected film and can avoid broad generated terms that create more downstream calls. | Without extra names, a title-free character/place reference may be missed. TMDB cast/characters are already fetched on film add, but may not cover plot objects. Manual editing increases setup effort. |
| Bound chat output and history; consider a separate model choice | Caps worst-case chat output; trimming/summarizing turns lowers repeated input. A cheaper model can help if quality holds. | A short cap can cut a useful recommendation or JSON trailer. Summarization may require an extra model call or omit taste context. Separate model variables increase configuration/test surface; one `OPENAI_MODEL` currently controls all three paths. |
| Use OpenAI Batch API for offline evaluation or precomputed terms | 50% API discount for work that can wait. | A browser shield and interactive chat need an immediate result; Batch has up to a 24-hour completion window and file/job plumbing. It is not the content script's existing 20-item synchronous batching. [OpenAI Batch API](https://developers.openai.com/api/docs/guides/batch). |

For privacy, the classifier sends candidate page text and relevant film context to the local app, which forwards it to OpenAI; it does not include URL or browsing history in the request. Chat forwards profile, film context, watchlist titles, and conversation messages. Automatic term expansion forwards title/year. Avoid presenting “local storage” as “fully local inference.” OpenAI says API data is not used for training by default, while its Chat Completions abuse-monitoring retention is generally 30 days; prompt caching may retain encrypted GPU-local tensors for up to 24 hours ([extension README](../../extension/README.md), [data controls](https://developers.openai.com/api/docs/guides/your-data)).

## Evidence needed before choosing

Record, per call path and configured model, request count, batch size, candidate-to-page-block ratio, `usage.prompt_tokens`, `usage.completion_tokens`, cached/write tokens where returned, error/timeout/incomplete-response counts, and latency. Aggregate counts without logging page text, URLs, profile values, or keys. Compare a fixed real-page and demo test set for spoiler misses, unnecessary blurs, and revealed/unchecked blocks. Use the formula above with **actual** usage and current pricing. A project spend alert or hard monthly cap can bound exposure; OpenAI documents that a hard cap returns `429`, is not instantaneous, and can interrupt functionality ([spend limits](https://developers.openai.com/api/docs/guides/spend-limits)). This note does not contain production usage measurements or a model-quality evaluation.
